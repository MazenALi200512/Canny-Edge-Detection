# Phase 4 — Compiler Optimization Analysis

## Methodology

The scalar pipeline (Gaussian, Sobel, magnitude, direction) was compiled at five
optimization levels and run three times each on QEMU (`vlen=128`, Vector extension
**disabled** so only scalar instructions are measured). Wall-clock time was recorded
using `std::chrono::high_resolution_clock`. The average of the three runs is used
to reduce QEMU jitter. Binary size was measured with `ls -s` on the ELF output.

> Note: QEMU is not cycle-accurate. Absolute times are meaningless; only the
> relative comparisons between flags are valid, since what changes between runs
> is the instruction count and structure, not the emulated microarchitecture.

## Analysis

### -O0 (no optimization)
Baseline. Every variable is spilled to the stack between statements, no inlining,
no dead-code elimination. The compiler emits one instruction per source operation.
Result: 394,157 µs average, largest binary at 45 KB.

### -O2 (standard release)
3.74× faster than -O0. The compiler applies inlining, constant propagation,
common-subexpression elimination, and loop-invariant code motion. Binary shrinks
to 29 KB because inlining removes call overhead and dead stores are eliminated.
This is the default flag used during development.

### -O3 (aggressive optimization)
7.01× faster than -O0 — the best runtime result. Enables additional loop
transformations (unrolling, strength reduction) beyond -O2. Binary grows to 37 KB
due to loop unrolling producing more code. The 1.87× improvement over -O2 shows
that the inner convolution loops benefit significantly from unrolling.

### -Os (optimize for size)
3.78× speedup, nearly identical to -O2 in runtime (104,402 µs vs 105,368 µs),
but produces the smallest binary at 28 KB. -Os disables transformations that
increase code size (loop unrolling, function cloning). Useful when flash storage
is constrained; for this pipeline there is no meaningful runtime cost vs -O2.

### -Ofast (unsafe math)
6.19× speedup, slightly slower than -O3 (63,696 µs vs 56,231 µs) despite being
a superset of -O3. -Ofast adds `-ffast-math` which allows reordering of
floating-point operations. Our pipeline is almost entirely integer arithmetic
(the only float use is `sqrt` in magnitudeL2 and `atan2` in direction, now
replaced with integer cross-multiplication). Since there is little floating-point
to reorder, -Ofast provides no additional benefit over -O3 and shows more timing
variance across runs.

## Auto-Vectorization Report

Compiled with `-O3 -fopt-info-vec-optimized -fopt-info-vec-missed`:

```
src/gaussian.cpp  — missed: couldn't vectorize loop
                    not vectorized: control flow in loop

src/sobel.cpp     — missed: couldn't vectorize loop
                    not vectorized: control flow in loop

src/magnitude.cpp — missed: couldn't vectorize loop

src/direction.cpp — missed: couldn't vectorize loop
                    not vectorized: control flow in loop
```

**The compiler failed to auto-vectorize any loop in the pipeline.**

### Why each loop was rejected

**Gaussian and Sobel — "control flow in loop"**
The inner loop contains boundary checks (`if (nx < 0 || nx >= width) continue`).
These create conditional branches inside the hot loop body. The GCC auto-vectorizer
requires a straight-line (branch-free) loop body to generate SIMD instructions.
The `continue` statement creates a control-flow edge that the vectorizer cannot
model as a predicated operation, so it rejects the entire loop.

**Magnitude — "missed: couldn't vectorize loop"**
The magnitude loop has no branch, but the compiler still failed. The likely cause
is the `std::abs` call on `int16_t` values — GCC may not recognize this as a
vectorizable absolute-value pattern for the target architecture without an
explicit vector abs intrinsic. On x86 GCC would use `pabs`; on RISC-V without
explicit RVV intrinsics the auto-vectorizer gives up.

**Direction — "control flow in loop"**
The original direction code used `atan2()` followed by `if/else` chains to
classify the angle into four sectors. Both the floating-point `atan2` and the
branching classification prevent vectorization. The integer cross-multiplication
replacement (Phase 2) removes the `atan2` but the `if/else` chain remains,
so auto-vectorization would still fail.

### What would fix it

For Gaussian and Sobel: pre-pad the image with a 2-pixel border of zeros so
the inner loop never needs boundary checks. The loop body becomes branch-free
and the compiler can auto-vectorize. This is a known technique used in
production vision libraries.

For Magnitude: replace `std::abs` with an explicit `max(x, -x)` pattern or
use compiler builtins. On some GCC versions this is sufficient for the
auto-vectorizer to emit vector absolute-value instructions.

This analysis motivated the decision to write RVV intrinsics by hand (Phase 6)
rather than relying on auto-vectorization, since the boundary-check structure
of the code makes compiler vectorization unreliable.

---

## Conclusion

The compiler provides a free 7× speedup at `-O3` over unoptimized code with
zero code changes. However, it cannot auto-vectorize any stage due to control
flow in the inner loops. This confirms that manual RVV intrinsic optimization
(Phase 6) is necessary to go beyond what the compiler can do automatically.
